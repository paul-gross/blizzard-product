# Toolchain

## The framework

The workshop is Storybook 10 on `@storybook/angular-vite`, its Vite-based Angular framework, which admits Angular 21 and
later and requires Vite 8 or later. Every Storybook package — `storybook` and `@storybook/angular-vite` — is a
`devDependency` of `web/package.json` pinned to one exact version, the newest 10.x that admits the workspace's Angular,
with no caret, so the framework moves only when a change moves it. No addon is installed. What Storybook 10's core
carries — controls, actions, viewports, and toolbar globals — is the whole workshop; the docs, interaction-testing,
accessibility, and Vitest addons are not added, and nothing from `storybook/test` is imported beyond `fn()` for wiring
an output to the actions panel.

The configuration is written by hand, never generated by `storybook init` or `npm create storybook`, and lives beside
the library it shows, in `web/projects/fleet/.storybook/`:

| File            | Holds                                                                                                                |
| --------------- | -------------------------------------------------------------------------------------------------------------------- |
| `main.ts`       | The framework and its options, the story globs, the static output directory, and `viteFinal`'s path aliases          |
| `preview.ts`    | The global stylesheets, the application providers every story renders under, the viewports, and the default viewport |
| `tsconfig.json` | The compilation the workshop builds with                                                                             |

## The install

`@angular/build` 21.2 depends on Vite 7.3.6 exactly, and `@storybook/angular-vite` needs Vite 8 as a peer, so a plain
`npm install` of the framework refuses the tree. Further collisions may surface against the workspace's exact Angular
and Vitest versions once the install is attempted. The workspace installs with `npm ci` from a committed lockfile, and
the install that lands must pass `npm ci` with npm's default peer checking. The first piece of work finds that install,
trying in this order:

1. **A direct Vite 8 `devDependency`.** Declaring `vite` at the top of `web/package.json` hoists Vite 8 for Storybook
   while `@angular/build` keeps its own Vite 7.3.6 nested beneath it, which a strict install admits without any
   override. It holds only if `ng build`, `ng serve`, and `ng test`, Vitest included, still resolve the Vite they were
   built against. Proving that is part of the piece: `npm run build`, `npm run test`, `npm run bundle-check`, and
   `npm run shell-sweep` all pass on the new tree.
2. **Scoped `overrides`.** An `overrides` entry in `web/package.json` that pins a peer under one named package only,
   never a top-level override of Angular, Vite, or Vitest that would change what the apps build with.
3. **Relaxed peer checking**, `legacy-peer-deps=true` in a committed `web/.npmrc`, only with the product owner's
   sign-off recorded on the piece's change. It reaches every install the workspace does, in CI, in provisioning, and on
   every developer's machine, so it is never chosen for convenience.

Whichever holds, the change that lands it says why in a comment beside the entry, in `web/package.json` or `.npmrc`, so
the next Angular upgrade knows what it carries.

## The build

The workshop runs through Angular CLI targets on the `fleet` project in `web/angular.json`, so it compiles with the
workspace's Angular context rather than the Storybook CLI's guess at one:

```json
"storybook": {
  "builder": "@storybook/angular-vite:start-storybook",
  "options": {
    "configDir": "projects/fleet/.storybook",
    "tsConfig": "projects/fleet/.storybook/tsconfig.json",
    "zoneless": true,
    "port": 6006,
    "ci": true
  }
},
"build-storybook": {
  "builder": "@storybook/angular-vite:build-storybook",
  "options": {
    "configDir": "projects/fleet/.storybook",
    "tsConfig": "projects/fleet/.storybook/tsconfig.json",
    "zoneless": true,
    "outputDir": "dist/storybook"
  }
}
```

`zoneless` is stated rather than left to the framework's default, because both apps run zoneless
(`provideZonelessChangeDetection`) and a part that only renders under Zone.js should fail here first. The framework
compiles ahead of time (`framework.options.jit: false` in `main.ts`) under the workspace's `strictTemplates`, as
`ng build` does, so a story whose template binds an input that does not exist fails to build instead of rendering blank.
`dist/storybook` sits under the workspace's existing `dist/`, which no wheel, image, or app build reads.

`.storybook/tsconfig.json` extends `web/tsconfig.json` and includes the story files, the `fleet` sources they render,
and `fleet/testing`. Each existing tsconfig excludes `**/*.stories.ts` so that stories never reach a production or test
compilation: `projects/fleet/tsconfig.lib.json` and `tsconfig.lib.prod.json`, both apps' `tsconfig.app.json`, and every
`tsconfig.spec.json`. The `test` targets' default include matches only `*.spec.ts`, so stories stay out of the unit-test
builder without a second exclude.

The framework does not read `tsconfig.json`'s `paths`, so `main.ts`'s `viteFinal` reads `compilerOptions.paths` from
`web/tsconfig.json` and maps each entry to `resolve.alias` — `fleet`, `fleet/shell`, and `fleet/testing` today, and any
entry added later — so the aliases have one home and the workshop resolves what the apps resolve.

`main.ts` globs `../src/lib/**/*.stories.ts` and `../../hub/src/app/shell/**/*.stories.ts`, the second reaching only the
hub shell's chrome ([stories.md](./stories.md) §The lens control). Nothing in `fleet` imports the hub; the glob is the
workshop's reach, not the library's.

## What every story renders inside

**The board's own stylesheets.** `preview.ts` imports, in order, exactly the stylesheets the `hub` build lists under
`styles` in `angular.json`: `@angular/cdk/overlay-prebuilt.css`, `fleet`'s `core/design/tokens.css` and
`core/design/scrollbars.css`, and `projects/hub/src/styles.css`. The hub's own sheet carries the board's body
background, text color, and monospace face, so a part sits on the surface it sits on in the board.
`tests/test_web_workshop.py` pins the two lists equal, read from `angular.json` and from `preview.ts`'s CSS imports, so
a sheet added to the board cannot go missing from the workshop. Storybook's backgrounds control is disabled
(`parameters.backgrounds.disable: true`), since the board has one theme and one surface.

**The application providers.** `preview.ts` applies one `applicationConfig` decorator to every story:

- `provideRouter([])`, so a part carrying a `routerLink` renders its `href` and a click goes nowhere.
- `{ provide: FLEET_CLOCK, useValue: () => FIXTURE_NOW }`, from `fleet` and `fleet/testing`, so every relative time a
  part shows — an age, a heartbeat, a duration still running — is measured from the same instant the builders date their
  records from, and a story reads the same on every visit. `FleetSecondClock` still ticks once a second, but each tick
  reads the same instant.

A story adds providers of its own only for what one part needs, and a part that needs a query client, a daemon token, or
a route snapshot has stopped being a part the workshop shows ([stories.md](./stories.md) §What stays out).

**The board's widths.** `preview.ts` declares the viewports the board is built for, named for the board rather than for
devices:

| Viewport     | Width  | Why it is there                                                                                      |
| ------------ | ------ | ---------------------------------------------------------------------------------------------------- |
| `phone-sm`   | 320px  | The narrowest width the mobile shell is proven at                                                    |
| `phone`      | 390px  | The phone width the board is reviewed at, and its right rail's width on the desktop board            |
| `mobile-max` | 767px  | The last width below `ViewportService`'s `(max-width: 767.98px)` cutoff, where the mobile shell ends |
| `desktop`    | 1280px | The desktop board                                                                                    |

A story renders at the reader's chosen viewport by default; a story that exists to show a narrow layout fixes its own
through `globals: { viewport: { value: 'phone' } }`.

## The commands

`web/package.json` gains three scripts:

| Script                    | Command                                                         | Does                                                                 |
| ------------------------- | --------------------------------------------------------------- | -------------------------------------------------------------------- |
| `npm run storybook`       | `ng run fleet:storybook --port=${BZ_STORYBOOK_PORT:-6006}`      | Serves the workshop, rebuilding on save                              |
| `npm run storybook:build` | `ng run fleet:build-storybook`                                  | Builds the static workshop into `dist/storybook`                     |
| `npm run story-render`    | `npm run storybook:build && node scripts/story-render-check.js` | Builds the workshop and renders every story ([gates.md](./gates.md)) |

`npm run storybook` needs no daemon, no seed, and no environment. It runs the same in the source checkout and in any
feature environment, against the kit as that checkout holds it. It reads `BZ_STORYBOOK_PORT` when the environment sets
one — every feature environment does ([workspace.md](./workspace.md)) — and otherwise serves on Storybook's own 6006.
The workshop is never published, deployed, or embedded in the wheel.

`mise.toml` mirrors the three as `web-storybook`, `web-storybook-build`, and `web-story-render`, beside the other
`web-*` tasks. `web/README.md` gains a section on the workshop beside the dev servers: what it shows, the one command,
the port, and that stories are for people and are held only by the render check and the kit's stories sweep.

## When Angular moves

Every Angular major waits for a Storybook release that admits it. The change that upgrades Angular upgrades the
Storybook packages in the same change, and `npm run story-render` is among the checks it must pass. Because the
framework is in preview, an option named here may be renamed or retired before it settles; the change that meets one
keeps the behavior this file states and updates the option.
