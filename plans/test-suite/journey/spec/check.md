# The consistency check

## The checker's split

`src/blizzard/tools/invariants.py` imports both the hub and the runner, which neither daemon may do. It splits along the
line its checks already keep: the runner's half, `RunnerInvariants` and the checks it runs, moves into the runner, and
the hub's half, `HubInvariants`, its checks, and the hub-scoped connection it alone may open, into the hub, each beside
the store it reads. `tests/test_layering.py`'s allowance for the hub-scoped exemption, and blizzard-context's
`architecture/system-shape/tenancy.md` that states it, move with the hub's half. `blizzard.tools.invariants` stays as
the composition both halves meet in, keeping `Invariants` and its signature, so the crash sweep and every in-process
caller go on as they are. The split changes no check and lands on its own.

## Two routes

| Daemon | Route                       | Lane and permission                                                                                       |
| ------ | --------------------------- | --------------------------------------------------------------------------------------------------------- |
| Hub    | `GET /api/admin/invariants` | The admin router: `reject_runner_principal` and `require_hub(Permission.TENANT_ADMIN)`. No new permission |
| Runner | `GET /api/host/invariants`  | The host's human lane, as `POST /api/host/ticks`                                                          |

Each runs its half of the checker and answers `200` with a `violations` list, each entry an `invariant` and a `detail`,
empty when every invariant holds. `invariant` is the check's slug, an open vocabulary a client shows as it finds it. The
hub's covers every tenant, since its checks are hub-wide by construction, and prefixes a per-tenant detail with its
tenant as today. The runner's covers every runner on the host.

A daemon answering is past recovery, since it reaps on start, so each route runs with `after_recovery` set, as the CLI
does today.

Both routes are additive to every supported release. Each lands with its OpenAPI document regenerated by
`mise run export-openapi`, the harness's wire types by `npm run generate:wire`, the board's clients by
`mise run web-generate-client`, and a change note under `changes/unreleased/`.

## One read

A check run against a live store can see a write between two of its statements: `OutboxCounterAboveSeq` reads counters,
then sequences, and the hub's fact checks load facts, then records. Each route runs its half inside one read
transaction, so every check sees the same moment: a deferred `BEGIN` held across the run on SQLite, and a read-only
`REPEATABLE READ` transaction on Postgres. The checks are proved against Postgres in the change that lands the routes,
since nothing has run them there before.

## The CLI's two modes

`blizzard dev check-invariants` keeps its offline mode unchanged: `--hub-dir` and `--runner-dir` against stopped stores,
which blizzard-context's manual procedures and the migration tests use. It gains a client mode that asks running
daemons: `--hub-url` for the hub, and the host's socket or `BZ_RUNNER_URL` for the runner, as the runner's client verbs
find it. The output and exit codes are the offline mode's: `invariants hold` and exit 0 when every check holds; each
violation as `[slug] detail` on standard error and exit 1 when any does; and exit 1 naming the daemon when one asked for
cannot be reached, since a check that did not run is never a pass. The `dev` group is outside the released CLI surface,
so the change owes no deprecation.

## The rule

blizzard-context's `architecture/crash-correctness.md`, where `bzh:invariant-checker` lives, gains the routes as the
checker's outside handle, in the change that lands them. `verification/blizzard/commands/test-tiers/crash-sweep.md`,
which says the sweep asserts through the CLI, is corrected to the in-process call it makes.
