# The consistency check

## The checker's split

`src/blizzard/tools/invariants.py` imports both the hub and the runner, which neither daemon may do. It splits along the
line its checks already keep, since no check reads both stores: the runner's half, `RunnerInvariants` and the checks it
runs, moves into the runner, and the hub's half, `HubInvariants` and its checks, into the hub, each beside the store it
reads.

Neither half may build its own collaborators where it lands. The runner's half builds its audit store through
`blizzard.runner.composition.build_host_stores`, which only composition roots may import, and defaults to
`LinuxProcessProbe` from `runner.process.internal`; the hub's half takes an `Engine`, where hub adapters take
`HubStoreConnections`. So each half takes its connections and its process probe injected, and the composition roots wire
them: `blizzard.tools.invariants`, which stays a composition root keeping `Invariants` and its signature, the hub's
composition, and the runner's app. The direct callers of `RunnerInvariants(engine)` and `HubInvariants(engine)` are
rewired in the same change to build through `blizzard.tools.invariants`: `tests/test_invariant_checker.py`,
`tests/runner_fakes.py`, `tests/runner_ingest_support.py`, `tests/test_pin_foundation.py`,
`tests/test_chunk_restart.py`, `tests/test_complete_claim_race.py`, `tests/test_hub_action_missing.py`, the crash
sweep's modules, and the store migration tests under `src/blizzard/hub/store/migrations/tests/` and
`src/blizzard/runner/store/migrations/tests/`. Their assertions do not change, and the split changes no check.

Serving the hub's half from a route adds a cross-tenant read outside the closed seam `bzh:hub-scoped-reads-confined`
names in blizzard-context's `architecture/system-shape/tenancy.md`. The split's change amends that rule to name the
invariant audit as its one exception, an admin-only read every check of which is a `SELECT`, and moves the hub-scoped
exemption's allowance in `tests/test_layering.py`, with the ast-grep ignores the rule carries, to the hub's half.

## Two routes

| Daemon | Route                       | Lane and permission                                                                                       |
| ------ | --------------------------- | --------------------------------------------------------------------------------------------------------- |
| Hub    | `GET /api/admin/invariants` | The admin router: `reject_runner_principal` and `require_hub(Permission.TENANT_ADMIN)`. No new permission |
| Runner | `GET /api/host/invariants`  | The host's human lane, as `POST /api/host/ticks`                                                          |

Each runs its half of the checker and answers `200` with a `violations` list, each entry an `invariant` and a `detail`,
empty when every invariant holds. `invariant` is the check's slug, an open vocabulary a client shows as it finds it. The
hub's covers every tenant, since its checks are hub-wide by construction, and prefixes a per-tenant detail with its
tenant as today. The runner's covers every runner on the host. A daemon runs one check at a time: a second request while
one runs is refused with `409`, so an impatient operator cannot stack scans of a live store.

Each route runs with `after_recovery` set, as the CLI does today: a daemon answering has marked its crash-orphaned
leases for resume on start, and its next loop pass reaps them. `ActiveLeaseProcessIsLive` probes processes live, outside
the read, so a caller checking right after a restart asks after the runner's first completed pass.

Both routes are additive to every supported release. Each lands with its OpenAPI document regenerated by
`mise run export-openapi`, the harness's wire types by `npm run generate:wire`, the board's clients by
`mise run web-generate-client`, and a change note under `changes/unreleased/`.

## One read

A check run against a live store can see a write between two of its statements: `OutboxCounterAboveSeq` reads counters,
then sequences, and the hub's fact checks load every chunk's facts, then its records. Each route runs its half inside
one read transaction on one connection, so every check sees the same moment. On SQLite, where the driver issues no
`BEGIN` before a `SELECT`, the route issues `BEGIN` itself and holds it across the run; on Postgres it opens a read-only
`REPEATABLE READ` transaction.

The hub's per-tenant checks do not read through one connection today: `HubInvariants` opens its hub-wide connections
separately, and the fact and record stores take fresh per-tenant connections through `HubStoreConnections.scoped`. The
routes' change gives `HubStoreConnections` a form over an already-open connection, scoping each tenant's reads within
it, and the checker builds the per-tenant stores through that form, so the facts-then-records race closes with the rest.
The offline mode and the crash sweep take the same path, over a transaction of their own.

The checks have never run against Postgres, and the matrix holds no method that would run them there: the tiers run
against SQLite, and its Postgres rows are the store baseline and the manual migration procedures. blizzard-context's
verifiability matrix gains a manual method, `blizzard:manual-postgres-invariants`, which runs both routes against a hub
on Postgres with seeded tenants and a host beside it, and it lands ahead of the routes, which record it as their proof.

## The CLI's two modes

`blizzard dev check-invariants` keeps its offline mode unchanged: `--hub-dir` and `--runner-dir` against stopped stores,
which blizzard-context's manual procedures and the migration tests use.

Its client mode asks running daemons, and finds each as the client verbs already do. `--hub-url`, or `BZ_HUB_URL`, names
the hub, and the command authenticates with the session `blizzard hub login` keeps, through the same session service the
`hub` group wires for its verbs, which the `dev` group gains. A caller who is not a hub administrator is refused by the
route, and the command says so. `--dir`, or `BZ_RUNNER_DIR`, names the host whose socket it asks, and `--runner-url`, or
`BZ_RUNNER_URL`, its local API over TCP instead. One invocation may name either daemon or both, and offline and client
options are never mixed in one invocation. Its client timeout is a minute, not the client verbs' fifteen seconds, since
the hub's fact checks read every chunk.

The output and exit codes are the offline mode's: `invariants hold` and exit 0 when every check holds; each violation as
`[slug] detail` on standard error and exit 1 when any does; and exit 1 naming the daemon when one asked for cannot be
reached, or refuses, since a check that did not run is never a pass. The `dev` group is outside the released CLI
surface, so the change owes no deprecation.

## The rule

blizzard-context's `architecture/crash-correctness.md`, where `bzh:invariant-checker` lives, gains the routes as the
checker's outside handle in the change that lands the routes.
`verification/blizzard/commands/test-tiers/crash-sweep.md`, which says the sweep asserts through the CLI, is corrected
in that change to the in-process call it makes.
