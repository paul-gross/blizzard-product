# Plan — `epic:test-suite/runner-tier`

The runner's service tests are the ones most bound to the Python. They build a `RunnerConfig` in memory, serve the
runner's local API from `build_hosted_app` on a thread inside the test, step its loop by calling `LoopWiring.tick_once`,
and read leases, escalations, and usage back through `SqlAlchemyRunnerStore`. None of that survives a move to another
language, and none of it should: a runner that can only be tested from inside itself has never had its outside proven.
This epic gives the runner the outside its tests need, then moves them.

## The tests it moves

| Group                           | Size     | Coupling today                                                                                                                                                                                               |
| ------------------------------- | -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Runner run in-process           | about 65 | `tick_once`, `build_hosted_app` on a thread, configuration through `dataclasses.replace`, store reads through the ORM.                                                                                       |
| Runner host started as a daemon | about 29 | The daemon is real, but its host layout and token files are written through internal classes, and graduation and ingest seed and read the runner's SQLite file because migrating that file is their subject. |

## Surfaces it builds

- **Driving the loop.** `blizzard-runner tick` already runs one REAP → PULL → FILL → ADVANCE pass from the CLI
  (`bzh:steppable-loop`), so tests call it as a subprocess instead of `tick_once`, and start `blizzard-runner host`
  instead of serving the app on a thread. The per-tick process cost is measured; if it matters, it is compared with a
  host running a short loop interval.
- **Configuration as files.** Runner configuration is written as TOML, or generated by `blizzard-runner init` flags, and
  the format joins the hub's as a documented contract.
- **The host layout as a contract.** The directory layout and token files a host reads are documented, so a test can lay
  them out without the classes that write them today.
- **Reading state.** For each value a test reads from the runner's store today — pending outbound facts, open
  escalations, leases, usage samples — the epic decides between an API or CLI read and declaring the SQL schema a
  contract that tests may query with plain SQL. The ORM is never the contract.

## Sharing

A runner-side test on the shared hub adds a runner in its own tenant and starts it on a store of its own, which is all
`initiative:multi-tenancy` promised it would need. Tests against the mock hub keep a mock hub of their own unless the
mock fleet grows tenants, since the mock is cheap to start and holds no migrations. The graduation, ingest, and
directory-ownership tests are about the store's files and keep dedicated runners; they may prepare those files before
the daemon starts, the one store access the initiative allows, and may stay in pytest if porting them buys nothing.

## Done

`tests/service/` holds nothing: every service test runs in the Playwright project, and any store-file test kept in
Python has moved to the pytest tier it belongs to.
