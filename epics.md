# Epics

The registry of blizzard's live epics: the capability areas the product is built from, in priority order — the order of the rows is the order of the plans behind them. An epic is a capability area, not a version, and it may land in slices. Each epic serves one or more destinations in [milestones.md](./milestones.md); this is a reference list of what is being built and why, not a status board — where an epic's slices actually stand is tracked in the milestone epic charts and in GitHub, and a slice that has fully landed resolves in [delivered.md](./delivered.md).

| Epic | Capability | Notes |
|------|------------|-------|
| `epic:security` (worker-lockdown slice) | Worker lockdown (D-087): permission profiles beyond the runner-configured skip-permissions default, network/credential blast radius, force-push protection, per-node permission config. | Live risk while dogfooding with real workers against real GitHub. A [`milestone:polyglot`](./milestones.md) spoke. Plan: [worker-lockdown](./plans/worker-lockdown.md). |
| `epic:board` (mobile slice) | The board complete from a phone: every read and every action the operator has at a desk, present and usable at thumb size — so being away from the laptop never means an operation waits. The gap today is coverage, not access: the board reaches a phone but not everything is there when you arrive. | Operational necessity: `milestone:centralized-hub` made the fleet reachable from anywhere, and each control missing on mobile quietly takes that promise back. Deliberately outside `milestone:homeostasis` — prioritized on its own. |
| `epic:ci-feedback` | Routing CI and review results back into the owning session, capped feedback rounds. | Feeds the existing merge-queue machinery. Plan: [ci-feedback](./plans/ci-feedback.md). |
| `epic:queue` (dependencies slice) | Chunks that know what they stand on: an operator-declared dependency between chunks — this one builds on that one — that the queue enforces. A chunk with an unmet dependency shows as blocked, naming the chunk it waits on, and cannot be claimed; when the prerequisite lands, it comes ready on its own. The flat ready order gains its first relation. | Operational necessity: a chunk stalled at human review leaves its dependent claimable today, and an agent that finds the ground it expected missing builds it again — one idea, implemented twice. Grouping covers coupling known before work starts; the edge covers work already split or already in flight. Plan: [queue-dependencies](./plans/queue-dependencies/index.md), which also scopes an optional story-map board view riding the same edges. Later queue slices (priority, aging) stay unpromoted. |
| `epic:self-sourced-work` | Work items living in the hub's own store: a built-in `hub` work source whose items — authored by operators today, and by the fleet's own nodes once later epics wire producers to the same door — enter the same intake as forge-born work, carrying an advisory priority their author states. The forge stops being the only door work can arrive through, and a hub with no forge at all becomes fully operable. | Operational necessity: today every observation the fleet makes about itself — a delivery that silently failed, a red gate on `master`, a finding no chunk owned — waits for a human to read it and file an issue before anything acts. A [`milestone:homeostasis`](./milestones.md) spoke. Plan: [self-sourced-work](./plans/self-sourced-work.md). |
| `epic:garden` | Standing tending of everything the fleet produces — the guidance it runs on and the code it writes: recurring evaluation passes that prune, consolidate, and re-route the harness rules, context docs, and node prompts, and architectural fitness evaluations that hold blizzard-context's declared constraints — layering, dependency direction, seam shape — against the codebase. Guidance stays small enough to be read and load-bearing enough to be followed; drift is named while it is one commit old rather than discovered as spaghetti. | Operational necessity, twice over: the corpus only accretes — every retrospective proposes rules, and no standing process removes anything — and the code accretes faster than human review can hold an architecture line, where a constraint binds only if something checks it. One discipline, tuning and trimming on a cadence, covers both. A [`milestone:homeostasis`](./milestones.md) spoke. Plan: [garden](./plans/garden.md). |
| `epic:transcripts` | Every agent conversation in one place: the transcripts workers produce — today Claude Code's runner-local JSONL, tomorrow each harness's own format — flow off their machines into one fleet-wide store, so mining them (a retrospective sweep, a pattern hunt) reads a single archive instead of visiting twenty runners. | Operational necessity: retrospective mining scales with the fleet only if its raw material does — a runner-local transcript is unreachable the moment the fleet outgrows one machine. A [`milestone:homeostasis`](./milestones.md) spoke. Plan: [transcripts](./plans/transcripts.md). |
| `epic:analytics` | Counting what the fleet actually does: collection and aggregation over the fleet's own behavior — which skills fire, which agents spawn, which context files get read, how often and from which nodes — rolled up into numbers an operator can query, so decisions about the corpus rest on evidence rather than impression. | Operational necessity: the first hand-run count ("how often are skills used?") overturned an assumption — agents constantly, skills nearly never — and every unread context file or unused skill is guidance paid for in tokens and maintained for nothing. Feeds `epic:garden`'s tending; reads naturally from the store `epic:transcripts` builds. A [`milestone:homeostasis`](./milestones.md) spoke. Plan: [analytics](./plans/analytics.md). |
| `epic:mutation-testing` | Proof the tests would notice: mutation testing over the suites — seeded defects that must turn the gate red, run against a change's own lines at delivery time and across the whole corpus on a cadence — so a green gate means behavior is asserted, not merely executed. | Operational necessity: an autonomous fleet acts on green without a human's doubt, so the suite's ability to fail is load-bearing. Scales the hand-run practice `bzh:mutation-review-selection` codifies. A [`milestone:homeostasis`](./milestones.md) spoke. Plan: [mutation-testing](./plans/mutation-testing.md). |
| `epic:cost` (attribution slice) | The price of a feature, where before only a night had one: spend rolled up from chunks and attempts to the work item and the landing it produced, with the trend over time — so the operator sees whether the factory grows cheaper or dearer per unit shipped. | Builds on the delivered core slice's usage facts and hub flow-through (see [delivered.md](./delivered.md)). A [`milestone:homeostasis`](./milestones.md) spoke. |
| `epic:ideation` | The fleet as a source of product ideas, not only of code: on a cadence, it reads the software as built against the charter and offers the operator a short brief of high-level feature directions worth exploring — recommendations to weigh, never work it files for itself. The registry stays human-owned; the fleet earns a voice in it. | A deliberate maybe: enters as an exploration, and whether its briefs earn their reading is what the first cadence decides. A [`milestone:homeostasis`](./milestones.md) spoke. |
| `epic:adapters` (breadth slice) | The harness seam with more than one occupant: Codex and OpenCode as first-class workers behind the same spawn/resume/verdict adapters Claude Code rides — selftested like any harness, chosen per fleet or mixed by node. | The seam and its Claude Code binding landed with the mvp's adapters work (see [delivered.md](./delivered.md)); this slice adds the occupants it was built to hold. A [`milestone:polyglot`](./milestones.md) spoke. |
| `epic:projects` | Project as a first-class grouping across the platform — of what to do and who does it: one hub hosts many projects, each with its own work sources and its work carrying its project from ingest to landing; one runner serves them all, hosting a local workspace per project. Three projects on a laptop means three workspaces and one runner, not three of everything. | Lands in two slices, hub then runner. A [`milestone:projects`](./milestones.md) spoke. |
| `epic:intake` | The intake workbench: a screen of its own where queued work is assembled rather than pasted — the operator browses and searches the work sources' open items, pulls the chosen ones through ingest, and shapes what lands: many chunks selected at once, grouped, ungrouped, inspected side by side. The board's per-card grouping controls grow into a surface built for working a backlog down. | The forge stays the backlog's home — this screen moves its items into the fleet with less friction, never defines work. Browsing means the work-source seam gains an optional enumerate/search capability, a deliberate loosening of id-addressed ingest decided here; a hub of many sources and projects reshapes the surface, so this follows `epic:projects`. Ungrouping asks of grouping what it cannot do today: splitting a folded chunk back apart. |
| `epic:ui-toolkit` | A component toolkit under the board instead of hand-rolled elements: a deliberate survey of the component libraries and developer-accelerating frontend frameworks the web surface does not yet use, one chosen on evidence, and the board's custom-built pieces migrated where the payoff is real — so the next small form or dialog is assembled from parts, not invented again. | Operational necessity: every small surface the board grows — a form, a picker, a sheet — is custom work to write, style, and maintain, and the count rises with each epic that touches the board (`epic:board`, the story map, `epic:self-sourced-work`'s authoring surface). A survey-then-adopt effort in the spirit of `epic:config`. |
| `epic:config` | The configuration surface: every operational constant as config, comparable-run tuning for the harness-engineer persona. | A survey-then-sweep effort rather than a large build. |
| `epic:chat` | Telegram bot (D-031): question notifications with one-tap answers, delivery confirmations — and the notification fan-out seam it is the first binding of. | The seam is built with its first channel: who subscribes to what, and how a chat identity maps to a hub user, are decided here. Plan: [chat](./plans/chat.md). |
| `epic:board` (reach slice) | The board installed on a home screen — a progressive-web-app shell — and question notifications surfacing through it. | Question notifications ride the fan-out seam `epic:chat` builds. Plan: [board-remote](./plans/board-remote/index.md). |
| `epic:team` | Team mode: shared visibility and multi-operator policy over one hub-arbitrated fleet — cross-machine arbitration is the hub's queue, never forge-native acquisition. | Builds on the human-auth work (`epic:board`'s remote slice). |
| `epic:batching` | Execution units, the heuristic packer, the LLM planner, conflict packing, batch failure semantics. | Parked by design — captured, not scheduled. Plan: [batching](./plans/batching.md). |
